# Ensemble v2: fresh-session handoff

Read [the root guide](../../CLAUDE.md) first. This guide applies to every v2 story,
including companion changes outside this directory. It is provider-neutral: the issue,
checked-in contracts and current branch are sufficient; do not require chat history,
another model's private memories, or access to a sibling application's secrets.

## Delivery: normal pipeline, and what "landed" does not mean

The 2026-09-10 branch-only exception is **retired**. `feat/ensemble-v2-foundation` merged to
`main` on 2026-09-12 via PR #1173; start v2 implementations from `main` like any other story,
and follow the repository's normal cycle and merge defaults. Inspect branch, worktree and
upstream before editing; preserve other work. A dirty shared tree is not permission to reset or
sweep it into your commit. Stop if the task's files overlap someone else's uncommitted changes.

**Merging to `main` releases this app (since #1207, 2026-09-15).** Since the cutover (#1357)
this app IS `https://ensemble.brndn.zip/`: CI builds it at `ENSEMBLE_V2_BASE=/` into the
`ensemble-web` image and the `deploy` job releases that tag to prod and then test on every
merge, asserting each host's public `/build.json` names the commit. It is gated by the required
`v2-checks` context (build + `checks/` Playwright suite) next to `checks` and `e2e-tests`. Treat
a v2 story as live production work: it reaches users, and a red v2 build or E2E blocks the
merge. `../v2-api/` is released by the same job, behind `/api/*` on the same origin.

The cutover was a **hard cut**: there is no v1 at `/` any more and no `/v1/` grace path, and
`/v2/*` redirects to the same path at the root (the one carve-out is `/v2/sw.js`, the tombstone
that retires the beta's worker — `hosting/README.md`). v1's browser data is reachable only
through the v1 import (#1274), which copies one way — v1's songs into this songbook, never a
write back to a v1 key — and old `?s=` links open best-effort (#1279). Accounts are on by
default (#1357); `?accounts=off` is the per-device way out, offered back on the songbook.
**A device that has never held an account still asks the server nothing** — not the session
read, and so not the account database either (`deviceMayHoldAccount` in `lib/account/feature.ts`,
which records why: on WebKit that one request, failing during an offline load, took the GUEST
songbook with it). Prod registration is an on-box policy value, not a repository one. The v1 source, its build
and its CI jobs were deleted in #1358; `public/` remains as the engine library this app imports. The plan is [the rollout](../../docs/design/ensemble-v2-rollout.md).

Human gates are unchanged: a device or listening gate is still a hard stop, and a merged commit
does not clear one. Record the commit SHA, checks and remaining gate so another agent does not
implement the same story again.

Use the local harness's installed workflow skills; their shared doctrine still supplies review,
provenance, safety and verification rules. If those skills are unavailable, follow the same
steps explicitly and report that limitation. Do not weaken a gate because another provider is
executing. Generated skill copies are renderer-managed, not task-local files to patch.

## Non-negotiable product and trust boundaries

- Fast guest accompaniment, a generous local songbook, and a music stand during playback.
  Accounts enhance those paths; they must not gate guest startup or require a server to play.
- Explicit Save commits a version. Automatic recovery retains a writer's unsaved experiment;
  it never silently uploads it. A later cloud acknowledgement cannot overwrite newer editing.
- Portable v1/v2 charts contain musical intent, not account/session/retry metadata. Preserve
  originals on conversion/import; unknown or corrupt data is not an empty-library success.
- The account-local database/outbox (`lib/sync/`) is wired to passkey sign-in and the UI
  (#1261 onward). Account code goes in `app/account/` and `lib/account/`; plain `fetch`, and
  `@simplewebauthn/browser` is the only new client dependency.
  `AccountScope` is a local fence, **not authentication**. Production authorization must come
  from a verified server session. Fake transports are contract tests, not cloud support.
- Never migrate/delete guest or legacy stores incidentally. Do not cache private API/auth
  responses or personalized HTML in the anonymous app shell. No credentials or chart contents
  in telemetry. Keep local safety, cloud confirmation and verified offline sounds distinct.
- The band engine (`../../band/`, `lib/band-host.ts`) plays; the old generators and the
  worker are gone (#1404). Unsupported chart
  semantics block with an explanation; full iReal compatibility is a target, not today's
  capability.
- Passkeys plus downloadable recovery code are approved. Hosting, backup/restore operations,
  production migration and public rollout still need their explicit gates. Do not invent an
  email reset, social account service, subscription tier or Docker mandate.

A change of fingering costs ONLY the shared notes that change finger (`fingerTransCost`, `REFINGER_COST`): the per-finger travel charge is gone (#1617). Measured over 5,760 charts (shell, triad and mixed, twelve keys, both instruments): capping travel at a lift and a place left 21 second fingerings no held note explained, all a barre chosen over a fingertip each by the count of fingers; with no travel term there are none, and as many notes stay held. So a grip takes its default fingering everywhere in a chart unless a neighbour holds a note under another finger (blues in B♭: every B♭7 `x 1 x 1 3 x` is 1-2-3). #1617 moved no grip. Every UKULELE chord, 7th or triad, is fingered as the ukulele is taught (#1681, `FingerOpts.ukulele`, set by `fingerRules` from the instrument; fingers only, no fret moved, and no guitar fingering changed). Three rules. (1) A ukulele shell is a strummed chord and goes through `taughtStrummed` with barres, not `taughtAmong`: the finger-per-note rule exists so a guitar shell's fretting hand can mute the strings it skips, and a ukulele shell skips none — D7 `2 2 2 3` is 1-1-1-2, Bm7 `2 2 2 2` one finger, B♭7 `1 2 1 1` 1-2-1-1, A♭maj7 `1 3 3 3` 1-3-3-3, B♭maj7 `2 2 1 1` 2-3-1-1, Gm7 `0 2 1 1` 0-2-1-1, and no ukulele grip shows four fingertips on one fret. (2) No barre lies on an open string (`barreOptions`; a guitar's strummed grips too since #1677): a flat finger reaches its strings from the palm side, so an open string of the grip numbered below the run is under it. D `2 2 2 0` is 1-2-3 (2-3-4 beside a chord that keeps two of those fingers), Asus4/Dsus2 `2 2 0 0` 1-2, C♯m `1 1 0 4` 1-2-4, Faug `2 1 1 0` 3-1-2, Dsus4 `2 2 3 0` 1-2-3 (from D two fingers stay and the ring finger moves up a fret); an open string beyond the fingertip is clear (Gm7 `0 2 1 1`, Gmaj7 `0 2 2 2` and Cm `0 3 3 3` are barres). This one is in `fingerOptions`, because the fingertip fingering it leaves is more than 4 dearer than the barre and was never on offer; no ukulele grip is chosen by fingering cost, so it moves no grip. (3) A ukulele chord leaves its default fingering only for TWO fingers that stay (`FingerOption.hold`, `heldFingers`, checked in `arrives`), or its one finger when it uses one (and since #1677 for one finger when one is all it moves, `holdFor`): a second fingering is offered as `needs: 'before'`/`'after'` and fingers left down as `'left'`, each with the count. One held finger dragged the hand a fret behind its place (`Am Dm E7`: E7 `1 2 0 2` was 2-3-0-4, now 1-2-0-3; `Cm Fm G7`: G7 `0 2 1 2` was 0-3-2-4, now 0-2-1-3); two still choose (Dm7♭5 `1 2 1 3` to G7 0-3-2-4, G to Em 0-4-3-2, Bm7♭5 to E7 2-3-0-4), one-finger chords keep their finger (Cmaj7 `0 0 0 2` after G7, C after Fm), and the table's printed alternatives take one (E♭ `0 3 3 1`). A guitar grip still takes a second taught fingering for one held note, except one that takes an open grip's hand off the nut (#1683, below). Also: the margin is measured from the cheapest fingering that is not a cramped barre, so A♭m7♭5 `1 2 2 2` stays 1-2-3-4 rather than 1-2-3-3 (on three strings the cheapest is never cramped, so no guitar grip is affected). The leftovers of #1617 and #1681, as a guitar teacher and a ukulele teacher settled them (#1677; fingers only, no fret moved on either instrument). GUITAR, three rules. (1) The open-string half of a barre's legality is every strummed grip's, not only a ukulele's: two notes on one fret under a sounding open string take a fingertip each (Em `x 2 2 0 x x` and A `x x x 2 2 0` 2-3, E♭ `x 1 1 0 x x` 1-2, Csus4 `x 3 3 0 x x` 3-4), and E5 `0 2 2 x x x` and A5 `x 0 2 2 x x` keep the index barre, their open string beyond the fingertip. A guitar shell's root barre is not asked. (2) A grip fingered FROM THE NUT takes the cheapest fingering with no fingertip ahead of its fret (`fingeredFromTheNut`, `aheadOfItsFret`): a chord that rings an open string and frets nothing past the 3rd fret, where a finger takes the fret of its own number and two notes on one fret that finger and the next. Open C `x 3 2 0 x x` is 3-2, G `x 2 0 0 x x` the middle finger, and those are what choose 2-3 over 1-2 in (1). The fingerings it passes over stay as SECOND fingerings (`needs: 'before'`/`'after'`): C as 2-1 into Am `x 3 2 2 x x` keeps both fingers, Em as 1-2 into C the middle finger, A as 1-2 into D the index. The rule is general, so it also fingers the open grips nobody asked about: a lone 3rd-fret note takes the ring finger (Csus2 `x 3 0 0 x x`), D5 `x x 0 2 3 x` and Asus4 `x x x 2 3 0` are 2-3, B♭dim `x x x 3 2 0` 3-2. A 4th-fret note is the hand moved up and is not asked (C♯dim `x 4 2 0 x x` stays 3-1). Shells are left alone: A7 `x 0 x 0 2 x` is still the index, because the same rule there would finger Dmaj7 `x x 0 x 2 2` as 2-3. (3) A shell's default is the in-position fingering where its cheapest is out of position and the in-position one is within the margin (`taughtAmong`): one shape, the maj7 on strings 4, 2 and 1, Fmaj7 `x x 3 x 5 5`, 1-3-4 cold where it was 1-2-3. The two swap prices and 1-2-3 stays free. And for both instruments: the same grip again under the same fingers is no change (`sameHand`, in `arrives`), so a marked second fingering waits through a repeated bar for the next chord that differs (C C Am keeps both fingers as C Am does). That was true only of what a fingering may sit beside; what it COSTS was still charged every bar, so an unmarked second fingering lost to the default once its chord lasted long enough. Since #1683 a fingering's own cost is paid once for a run of one chord (`sameFingers`, in `planFingers`), and a chart fingers the same whatever the bar count (below). UKULELE. `FingerOpts.ukulele` is read off the instrument, so the three-string power chord (G5 `0 2 3 x`) gets the ukulele's rules too. In `barreOptions`: the little finger never lies flat (the closed E shape `1 4 4 2` / F♯ `3 6 6 4` is 1-3-4-2 with 1-3-3-2 second, the aug shape `1 4 4 3` the same, the sus4 shape `1 3 4 4` 1-2-3-4, and `1 1 4 4` is never 1-2-4-4), and only the index lies flat under another finger (the G shape `7 9 10 9` is 1-2-4-3 at every fret, the dim shape `5 6 5 3` 2-4-3-1). The default (`ukuleleDefault`) is the cheapest fingering with no finger ahead of its fret, counted from the hand's own position (E5 `4 4 0 2` is 3-4-1, not 2-3-1), then: not a ring finger arched over two lower strings (`archedBarre`: E♭m `3 3 2 1` is 3-4-2-1, the barre second), and the index across the note the middle finger would hold beside it (`indexAcross`: the sus4 shape `3 3 1 1` / `4 4 2 2` is 3-4-1-1). A one-note chord takes the finger of its fret by rule (2) above: C the ring, Am and Cmaj7 `0 0 0 2` the middle; a fuller open chord is still printed from the index (D 1-2-3, G 1-3-2). And a marked fingering needs as many fingers to stay as it moves off the default, up to two (`holdFor`): C Fm C keeps the ring finger on the A string throughout (Fm 1-0-2-3), C Cm C the same through Cm's book 1-2-3, while E7 after Dm and G7 after Fm still need two and keep their book fingering. Known limits. Dsus4 as 1-2-4 over a D left down is priced as a stretch and not offered, and E `4 4 4 2` is still the ring barre 3-3-3-1. A second fingering can still be an awkward one where it keeps two fingers (Esus2 `4 4 2 2` as 3-3-1-2 beside Esus4 `2 4 0 2`). ## Verification and receipt

Iterate with the smallest relevant test selection; before handing off implementation, run the
repo gates and the v2 gates affected by the story. From the repository root:

```sh
npm run validate
npm run test:browser
npm run test:sync
npm run build --prefix prototypes/v2
npm run test:e2e --prefix prototypes/v2
```

`validate` also runs the formatter: inspect its diff and do not commit unrelated formatting.
The separate sync configuration includes its browser files explicitly; register any new file
there so both engines actually run it. Node/happy-dom is not proof of IDB transaction behavior.
Coordinate heavy browser suites instead of competing for their ports. Emulator success is not
physical iPhone/Edge acceptance, and audio assertions are not human by-ear approval.

Test deployment is optional per story and never inferred from a push: `scripts/deploy-test.sh`
releases a pushed branch's `ensemble-web` image to the test host (read the deploy-test skill
first). Identify exact artifact/commit and
report deployment separately from local/CI evidence. Never call an old deployed build current.

Each handoff needs: issue + commit SHA; changed surfaces; acceptance checklist with actual
evidence; checks run and results; unrun/failed gates and why; deployment status; next dependency.
Record genuine failures without editing expectations, skipping tests or asserting the intended
behavior already exists. Auth/ownership/concurrency changes need an independent correctness and
security review; synth or subjective music changes retain their human listening gate.

## Economical, cross-provider execution

Use the repository's provider-neutral `model/economy`, `model/balanced`, `model/frontier` labels.
The current routing pairs those with Haiku/Luna, Sonnet/Terra, and Opus/Sol respectively; these
are workflow roles, not a guarantee about availability, subscription limits or equal capability.
Precise tests/mechanical tasks fit economy; bounded implementation fits balanced. Authentication,
concurrency, destructive migration or unresolved musical meaning requires frontier-level review
and any applicable human decision. Escalate when the task exceeds the specified boundary.

Give each fresh session one issue. Pass this guide and that issue, not the whole conversation.
Use one integration owner: do not run separate Claude and Codex sessions writing the same
branch concurrently. Parallel work requires verified disjoint files and owner-controlled
isolation/integration; shared fixtures, configs and the large app component are overlap too.

Suggested prompt once a child is filed and ready:

> Work on Ensemble v2 issue #NUMBER. Read CLAUDE.md and prototypes/v2/CLAUDE.md, then the
> issue and its dependencies. Branch from main and run the normal cycle. A merge releases this
> app to production, whether the story touches `public/` or only `prototypes/`. Stay within
> acceptance criteria, stop for unresolved decisions and human gates, and leave a test/commit
> receipt.

The broader design parents are not single implementation tasks. Pick a ready child; never run
an unattended cycle across the entire account or full-iReal umbrella.
