# Decisions: the repository

The repository and how work is done in it: the test suite and its time budgets, the tracker and the pipeline, hosting, CI and the release.

## 2026-11-15: three styles inside ten seconds

The property suite cost one style 8.9 s of its 10. With three it took 23 s on a quiet machine. Measured before changing anything: nearly all of it is rendering takes (a take is 13 to 28 ms and a style's run renders about 500); the engine's profile is flat (the random streams 15%, the soloist's likeness 11%, nothing else over 6%), so there is no quick doubling to be had there; and running fifteen test processes on this machine gives the parallelism of about three, because every file rendered the same takes again.

- **One process per style** (`scripts/test.ts`, `--test-isolation=none`): a style's property files run together and a take is rendered once. The styles run side by side.
- **A push plays two seeds; `pnpm test:full` plays six** (`ENSEMBLE_SEEDS`, 60 s budget). `docs/TESTING.md` allows exactly this ("a small seed count on every push and a larger one nightly"). The full run is for before a listening gate and after a merge that changes what a player chooses. A floor on how many cases a property met is written for six seeds and scaled (`enough`).
- **A push samples three things the full run plays whole**: the take played twice for "the same seed is the same take" (one in three of seed 1's); the chart corpus under "a chart with mistakes still plays" (each style a different third); the soloist's special takes (every other kind per chart, slow or medium tempo by turns for the horn).
- Result on a quiet machine: push 9.4 s with three styles (6.1 s with the blues alone), full 19 s. The limit was not raised. The margin is thin: the jazz piano has yet to land, and the next thing to give is the four-minute jams under "the piano stays in its part of the keyboard".
- Halving the seeds alone was tried first and saved little, because every file was still rendering its own copy and half the renders were not `takes()` at all.

## the engine's budget counts written meters as it counts styles (stage 6, 2026-11-17)

- **The rule is restated, with Brandon's word** ("i'm on board with your recommendations for the test suite ... we're packing a lot of functionality in here"). It was written for eight styles in 4/4; there are now 22 written style-meters, each held to every property. On a push: 10 s for three styles, 2 more for each style after the third, and 2 more for each meter beyond 4/4 that the style with the most of them has written. That is 24 s today (five styles have written two) and 26 when jazz has three. The six-seed suite is three times the push budget (72 s today) in place of a flat 60.
- **Why by the style with the most meters and not by the count of style-meters**: the styles are tested side by side, so the suite takes as long as its longest style, and a meter written by a style that has few costs the suite nothing.
- **Why not sample harder instead**: the push suite already plays the other meters on one seed; thinner than that and a fault in six or twelve is found at the gate and not at the push.
- **What is still rationed**: the rules. A new property, a new kind of take or more seeds still has to fit, by consolidating or deleting. The scorecard's and the smoke journeys' budgets are as they were.

## production follows every green merge (2026-11-21, #2266)

Brandon: "we should set up proper ci/cd so we don't have to think about deploying to prod". Asked when production should get a new build, he chose every green merge. Production had last been released by hand on 2026-11-18 and was 42 commits behind `main`.

- **Four jobs, in order** (`.github/workflows/release.yml`, called by `ci.yml`): `plan` says what is released; `test` releases the image to the test site and confirms the site serves the commit; `journeys` runs the smoke journeys against the test site as a visitor reaches it; `production` releases the same image to production and confirms it the same way. A job that fails stops the ones after it, the run is red, and production keeps what it had. A red run is the notice; there is no other alerting. A journey that failed for no reason of the commit's is run again from the failed job.
- **The journeys run where the release key is not.** The old release job ran none of the repository's code. The journeys need `pnpm install` and a browser, so they have a job of their own with no secret and no tailnet; the two jobs that release check out `.github/` only and run the release action (`.github/actions/release/`: join the tailnet, the scoped key, `release <stack> web sha-<commit>`, wait for `build.json`) and nothing else. A first draft ran all of it in one job; the review pointed out that a dependency's script would then run on a tailnet node that accepts the LAN's routes.
- **One release at a time, whole, none dropped**: the lock (`concurrency: release`, `queue: max`) is on the job in `ci.yml` that calls the release, so it covers all four jobs together; with the default queue of one, a release waiting its turn is cancelled by the next to arrive.
- **A merge never moves a site backwards.** Releases take their turn in the order their builds finished, not the order of the commits. So a merge releases only the tip of `main`: `plan` asks GitHub where `main` is when the run's turn comes, and a commit `main` has moved on from is not released (the run stays green and says so), since the newer commit's run does it, or has. The release action asks again just before it speaks to the host, because a failed job run again later keeps the plan its run was given (the second review's finding: a stale run's `journeys`, run again after a newer release, would have put the older commit back on production). The cost: if that newer commit's build fails, the older one is not released either, until the next green merge.
- **The run by hand puts production on a named commit** (`gh workflow run ci -f commit=<sha>`, the tip of `main` if none; `-f test=true` for the test site too). It builds nothing and runs no journeys: it is for putting production back, and a journey failing on the test site should not stand in the way of that. The commit is read from the environment and used only once it matches 40 hex characters. It must be a commit of `main` (asked of GitHub: the registry also holds the old version's images, so an image alone is not proof) and must have an image (asked of the registry without a login: the package is public, checked 2026-11-21), both before the host is touched. The job needs no permission beyond `contents: read`. **A restore lasts until the next merge**, which moves production forward again; that includes a merge whose release was already waiting when the restore was run, so it is run when nothing is releasing.
- **What follows from it.** A docs-only push releases too (skipping it needs path filters that interact with the required `build` check; left alone).
